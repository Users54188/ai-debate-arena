## 修订说明（v1.0 → v2.0 改了什么、为什么）

| # | v1.0 原设计 | v2.0 修订 | 原因 |
|:---:|------|------|------|
| 1 | 10 周排期（7.17 起） | **8 周排期（8.10 起，9.25 首次提审）** | 截至 8.8 仓库无代码，原排期已延误 3 周；10.17 为大赛硬截止，必须预留审核被拒的缓冲 |
| 2 | 端侧 3 亿参数模型分流 70% 分析 | **降级为 W1 证伪验证项，默认全云端** | `wx.inference.classify` 与"内置 3 亿参数模型"均无官方文档来源；真实 API 为 `wx.createInferenceSession`（Beta、需自带 ONNX 模型、仅真机调试），自建谬误分类模型超出赛程工期 |
| 3 | Token 测算：单人会话 ~2000 Token，2000 DAU 够用 167 天 | **重算：单人会话 ~11000 Token，60 天预算约支撑 1500 会话/天** | 原测算漏掉了每轮调用重发上下文 + 多 Agent 调用倍数（详见 1.3） |
| 4 | 无限流设计 | **每日会话配额 + 客户端维度限频作为产品机制** | Token 是硬约束，防脚本刷量 |
| 5 | 云函数内串行编排、无流式 | **客户端编排 + `wx.cloud.extend.AI` SSE 流式** | 辩论模式 3 次串行非流式调用 = 用户等待 15-30 秒，体验不可接受 |
| 6 | 免费额度表按旧配额制（云函数 10 万次/月等） | **改为资源点套餐口径** | 成长计划二期个人版环境为资源点套餐，旧数字已失效 |
| 7 | 无合规设计 | **AI 标识 + 输入/输出双向审核 + 话题白名单列入 W1-W2 基础设施** | 《人工智能生成合成内容标识办法》已施行；UGC 话题广场移出售前范围 |
| 8 | ChatUI Kit（未证实存在） | **自建对话 UI（WeUI + 自定义组件）** | W1 验证结案：官方文档无此组件；真实存在的官方对话组件为 CloudBase Agent UI（可选替代，未采用） |
| 9 | D3.js 逻辑链可视化 | **Canvas 2D 自绘** | 小程序无 DOM，D3 无法运行 |
| 10 | 群聊辩论赛、话题广场 | **移出售前范围（赛后迭代）** | 保核心闭环，为审核缓冲让路 |
| 11 | 无 Prompt 评测机制 | **评测集 + 云函数 evalRunner** | 苏格拉底追问质量是产品命脉；注意免费额度禁止在小程序/云函数之外的来源消耗，评测必须走云函数 |

## 一、技术栈总览

### 1.1 选型矩阵

| 层级 | 技术选型 | 说明 |
|------|------|------|
| 前端框架 | 微信小程序原生 | 原生性能最优 |
| 对话 UI | **自建组件 `chat-stream`（WeUI 2.0 基底）** | W1 已验证：官方无 ChatUI Kit / ai-chat-view 文档；官方对话组件为 CloudBase Agent UI，不满足多角色定制需求，不采用（见 docs/w1-verification.md） |
| 状态管理 | app.globalData + 页面级状态机 | 辩论/双人模式的"角色发言顺序"由页面状态机驱动 |
| 后端 | CloudBase 云开发 | 成长计划个人版环境（资源点套餐），6 个月有效 |
| 云函数语言 | Node.js 18 | 仅承载非实时路径（状态、报告、审核、配额） |
| 数据库 | CloudBase 文档型数据库 | 会话、报告、用户、配额四表 |
| LLM 接口 | `wx.cloud.extend.AI`（小程序端直调，SSE 流式） | 混元 hy3 / hy3-preview；要求基础库版本以小程序端官方文档为准，W1 验证 |
| 端侧推理 | `wx.createInferenceSession`（**可选增强，W1 证伪验证**） | 验证失败则不启用，不影响任何核心功能 |
| 图片生成 | Canvas 2D 纯绘制 | 不消耗 AI 生图额度（10 万张额度原样保留） |
| 版本管理 | GitHub | 已建仓库 |

| 资源 | 计费口径（资源点套餐） | 需求量级估算 | 是否够 |
|------|------|:---:|:---:|

### 1.3 Token 消耗测算（v2.0 重算）

**单次调用成本模型**（⚠️ 估算值，W2 用接口返回 `usage` 字段实测校准）：

```
单次 LLM 调用 ≈ system prompt 400 + 会话上下文 500 + 用户输入 80 + 模型输出 150 ≈ 1200 Token
```

> **W2 评估基线说明（2026-08-10）**：v2.0 苏格拉底 system prompt 由 ~250 字增至 ~750 字
> （对抗性强化，见 prompts/socrates.md 变更日志），单次调用约 +350~450 Token，
> 本节 v1.0 估算的"system prompt 400"需按 +400 上修；L1 单会话（10 轮 + 摘要）
> 约 +3.5~4.5k Token。**实测校准流程**：真机走满 10 轮 L1 会话，取 3 个以上样本，
> 汇总 token_usage 表按 sessionId/mode 关联的实际 prompt_tokens + completion_tokens，
> 用实测均值替换本节估算值并标注样本数（提报材料引用实测值）。
> evalRunner 云函数全量跑评测（42 条用例 × 2 次调用 ≈ 10 万 Token）同样计入 AI 资源包
> 消耗，已按"每天最多一次全量"防刷（cloudfunctions/evalRunner）。

**分模式测算**（上下文随轮次滚动，取均值估算；⚠️ 含 system prompt 上修前的旧口径）：

| 场景 | 计算 | 每次 Token | v1.0 估值 | 偏差 |
|------|------|:---:|:---:|:---:|
| L1 单人（8 轮 + 报告） | 8 轮 × 1200 + 报告 1500 | ≈ 11,000 | 2,800 | 低估 ~4 倍 |
| L2 双人（6 用户轮 × 2 角色） | 12 次调用 × 1300 | ≈ 15,600 | 3,500 | 低估 ~4.5 倍 |
| L3 辩论（3 轮 × 3 角色） | 9 次调用 × ~2000（上下文递增） | ≈ 18,000 | 5,000 | 低估 ~3.5 倍 |
| 会话摘要（第 9 轮起触发） | 1 次调用 × ~800，摊入会话 | ≈ 800 | 未计入 | — |

**总预算推演**：

```
评审期按 60 天计：10 亿 ÷ 60 天 ≈ 1670 万 Token/天
按 L1 为主（人均日耗 ≈ 1.5 万 Token，含少量 L2/L3）：
1670 万 ÷ 1.5 万 ≈ 1100 DAU 可持续 60 天
```

**结论**：评审期实际 DAU 预计在数百量级，额度可覆盖，但**必须**配合第 1.4 节限流机制；v1.0 "2000 DAU 用 167 天"的表述作废，不得出现在提报材料中。

### 1.4 配额与限流（产品机制，非可选）

| 限制项 | 规则 | 实现 |
|------|------|------|
| 每日会话配额 | L1 ≤3 次/日，L2 ≤2 次/日，L3 ≤1 次/日 | `user_quota` 表按 openid+日期记录，前端进入页面前校验 |
| 单会话轮次 | 封顶 10 轮，到达后强制进入报告环节 | 对话状态机控制 |
| 接口频率 | 对话类接口单用户 ≤2 QPS | CloudBase 安全管控 → 客户端维度限频（按 openid） |
| 用量告警 | 资源包 80%/90%/100% 三级（官方公众号通知） | 达 80%：暂停 L3；达 90%：全部会话轮次压至 5 轮 |
| 异常调用 | `EXCEED_CONCURRENT_REQUEST_LIMIT` 自动退避重试（最多 2 次） | 请求封装层统一处理 |

## 三、核心模块设计

### 3.1 对话引擎（客户端编排 + 流式）

```
┌─────────────────────────────────────────────────┐
│                小程序前端                         │
│                                                  │
│  页面状态机：决定"下一个该谁说话"                  │
│  ├ L1: 用户 → 苏格拉底 → 用户 → …（8-10 轮）      │
│  ├ L2: 用户 → 专家 → 苏格拉底 → 用户 → …          │
│  └ L3: 正方 → 反方 → 裁判（每轮顺序流式发言）      │
│         │                                        │
│         ▼                                        │
│  ai-stream.js                                    │
│  ├ wx.cloud.extend.AI.streamText (SSE)           │
│  ├ 渲染节流：缓冲 token，~120ms 批量 setData      │
│  ├ 上下文组装：system + 最近 8 轮原文 + 滚动摘要   │
│  └ 输入前置：security.msgSecCheck                │
├─────────────────────────────────────────────────┤
│  CloudBase                                       │
│  ├ sessionStore：轮次落库、摘要触发、配额扣减      │
│  ├ generateReport：结束时结构化提取 + 评分        │
│  └ 数据库：sessions / reports / users / quotas   │
└─────────────────────────────────────────────────┘
```

**辩论模式时序（L3 单轮）**：

```
客户端发起正方调用（流式上屏，打字机效果）
  → 完成后发起反方调用（context 含正方本轮发言）
  → 完成后发起裁判调用（context 含双方发言）
  → 轮次 +1，落库，展示投票条
```

每个角色发言前有"对方正在组织语言"占位态，把串行等待转化为观赛节奏感。

### 3.2 端侧推理（降级为可选增强）

**W1 证伪验证清单**（0.5 天，真机执行）：

1. `wx.createInferenceSession` 在当前基础库是否可用？支持哪些算子/模型体积上限？
2. 是否存在任何官方预置文本分析模型？
3. 开发者工具不支持该 API 的情况下，真机调试链路是否可接受？

**决策规则**：

- 验证失败或模型不可得（预期大概率）→ 代码中完全移除端侧路径，谬误识别由苏格拉底 prompt 本身承担（其职责已含揭示谬误），报告环节的谬误标注由 `generateReport` 的 LLM 结构化提取完成。**提报材料中不再出现"端侧分流"叙事。**
- 验证成功 → 仅用于一个场景：用户发送后 200ms 内给出"论证结构速览"的即时 UI 反馈（体验增强），**不参与**任何影响正确性的判断，也**不注入** LLM 上下文（避免小模型误判锚定苏格拉底方向）。

### 3.3 多角色编排要点

```javascript
// miniprogram/utils/ai-stream.js（示意）
async function* streamRoleReply({ role, sessionId, userMessage }) {
  const { recent, summary } = await loadSession(sessionId); // 见 3.4
  const messages = [
    { role: 'system', content: PROMPTS[role] },
    ...(summary ? [{ role: 'system', content: `更早的对话摘要：${summary}` }] : []),
    ...recent,
    { role: 'user', content: userMessage },
  ];
  const res = await ai.streamText({ data: { model: 'hy3-preview', messages } });
  for await (const chunk of res.textStream) yield chunk; // 页面侧节流渲染
}
```

**角色差异化参数（防同质化）**：

| 角色 | temperature | 输出长度约束 | 附加要求 |
|------|:---:|------|------|
| 苏格拉底 | 0.7 | ≤3 句 | 只提问不回答（见 prompt 规范） |
| 专家 | 0.5 | ≤200 字 | 类比 + 框架，主动留"可追问的钩子" |
| 正方/反方 | 0.9 | ≤150 字 | 必须回应对方上一轮 + 提出新论点 |
| 裁判 | 0.2 | 结构化 JSON | 按 rubric 分别点评双方亮点/漏洞，禁止和稀泥 |

### 3.4 对话记忆（修订）

```
sessions 表
├── openid: string     # 云函数写入时显式注入（_openid 系统字段不会自动注入）；getQuota 按此统计每日配额
├── recent: array      # 最近 8 轮原文（环形，写入时裁剪，保证苏格拉底可引用原话）
├── summary: string    # 第 9 轮起触发滚动摘要（1 次 LLM 调用 ≈800 Token，已计入测算）
├── round: number
├── mode / topic / status / createdAt(serverDate) / updatedAt
```

- v1.0 中"存摘要"的文字与 `push` 全文代码的矛盾已消除：recent 存原文但硬裁剪，summary 只覆盖更早内容。
- 摘要由 `sessionStore` 在轮次越界时触发，异步执行不阻塞对话。

### 3.5 数据模型（其余表）

```
reports
├── userId / sessionId / mode
├── logicChain: {nodes, edges}     # generateReport 结构化提取
├── fallacies: [{type, quote}]     # quote 为用户原话，保证可追溯
├── strategyTags: [{round, type}]  # ★ 每轮追问策略标注（预设/证据/边界/后果/定义）
├── score / highlights / shared / createdAt

users
├── _id: openid
├── rank / totalSessions / totalRounds / avgScore / winRate / createdAt

user_quota（★ 新增）
├── _id: openid + '_' + yyyyMMdd
├── l1Used / l2Used / l3Used / updatedAt

topics_v1（静态白名单集合，约 50 条预置辩题）
├── title / category / difficulty
```

> 话题广场（UGC 投稿）移至赛后迭代。赛前所有辩题来自审核过的白名单，从源头消除 UGC 审核风险。

### 3.6 评分算法

与 v1.0 相同（基础分 30 + 深度分 40 + 修正分 30），补充实现机制：

- **深度分依赖的"追问策略标注"**由 `generateReport` 中的一次 LLM 结构化调用完成（输入苏格拉底全部发言，输出 `strategyTags` JSON），不再依赖端侧模型。
- **谬误率**同样来自该次调用的 `fallacies` 输出。
- 即：报告环节 = 1 次主生成 + 1 次结构化标注，共 2 次调用，已计入 1.3 测算。

### 3.7 合规与安全（★ v2.0 新增，W1-W2 落地）

| 要求 | 依据 | 实现 |
|------|------|------|
| AI 生成内容显式标识 | 《人工智能生成合成内容标识办法》（2025-09-01 施行） | 对话页常驻"AI 生成"角标；海报含 AI 生成说明 |
| 保留官方免责标记 | 混元接口返回 `note` 字段要求不得删除修改 | 展示层保留或按平台规范处理，代码中禁止 strip |
| 用户输入审核 | 平台内容安全要求 | 输入进对话前过 `security.msgSecCheck`（securityCheck 云函数） |
| AI 输出审核 | 同上 | 启用流式输出审核；收到 `finish_reason=sensitive` 时撤回已上屏内容并替换为兜底文案 |
| 类目选择 | 深度合成类目需额外资质 | 优先申报"工具"类目，提审前对照最新类目要求确认 |
| 敏感话题防护 | 辩论产品天然风险 | 赛前辩题全白名单；苏格拉底/裁判 prompt 内置"涉政涉敏话题主动终止并切换"指令 |

## 六、开发注意事项

### 6.1 Prompt 管理

- 所有 prompt 集中于 `prompts/`，改动走 Git 版本记录（commit message 写改动原因）
- **任何 prompt 改动必须先跑 evalRunner 回归**，通过率不降方可合入
- 评测一律通过云函数执行（免费额度合规来源），禁止在 AI 编程工具/本地脚本中直连消耗资源包

### 6.2 流式渲染

- token 缓冲后批量 `setData`（~120ms），禁止逐 chunk 刷新
- 真机测试为准（模拟器与真机流式行为有差异）
- `finish_reason=sensitive` 的撤回兜底文案预置在组件内

### 6.3 云函数

- 单一职责；对话路径不依赖云函数，无超时压力
- 报告类超时设 30s；统一返回 `{ code, data, msg }`
- 冷启动可接受（均为非实时路径）

### 6.4 Token 监控

- 每次调用落 `usage`（prompt_tokens / completion_tokens）至 token_usage 表，每日汇总
- W2 完成实测校准后，1.3 节所有 ⚠️ 估算标注替换为实测值，提报材料引用实测数据
